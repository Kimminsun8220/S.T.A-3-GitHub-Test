# 기획 가설과 검증 · 새 분석의 기본 형식

먼저 career-insight.md의 사실·근거·직무 관점 기준을 적용한다. 새 분석에는 아래 schema_version 2를 사용한다. 기존 insight.py는 이전 형식 재현용으로 보존한다.

## 첫 화면과 상세 본문

- Summary: 상세 분석의 핵심 의미를 한 문장, 권장 40~70자·최대 90자로 적는다. 3줄 기사 요약은 상세 본문에만 둔다. 기업 의도를 요약할 때도 가설 표현을 유지한다.
- 기본 표: Title / Date / Category / Company / Summary / Career Use. Source는 숨기고 원문과 매체는 상세 본문에 보존한다.
- 상세: 사실 → 변화 → 비교 → 기획 가설 → 사업/상품 관점 → KPI와 의사결정 → 내가 담당자라면 → 검증 Action. 기존 취업 활용·한계·출처는 유지한다.

## 분석 JSON 확장

최상위: `{"schema_version": 2, "analyses": [...]}`. 각 행은 기존 분석 필드에 `planning`을 추가한다.
- planning.summary: 짧은 한 문장 문자열.
- planning.comparison: 하나 이상의 객체. target(비교 대상), known(확인한 차이 또는 비교 설계), unknown(미확인 차이·추가 확인) 문자열.
- planning.hypothesis: text(기업 선택 이유의 가설), basis(원문 근거), verify(검증할 자료·방법), refute(가설이 약해지는 결과) 문자열.
- planning.decisions: 모든 KPI마다 정확히 하나. kpi(기존 KPI 이름과 일치), basis(대조군·기간·분모 등), supports(지지 결과에 따른 결정), otherwise(반대 결과에 따른 결정) 문자열.
- planning.roles: product, business 문자열. 두 직무 담당자라면 무엇을 조사해 무엇을 결정할지 제안한다.
- action은 기존 task/deliverable/minutes를 사용한다. 산출물에 가설 검증 설계와 결과 기록 방법을 포함한다.

## 해석의 품질

- 일반 모델·도입 전·이전 한정판·경쟁 대안 중 적합한 기준을 반드시 정한다. 실제 비교 자료가 없으면 비교 설계와 미확인 값을 적고 우열을 단정하지 않는다.
- 새 가격·성능·혜택 차이를 사실로 추가할 때는 원문을 확인하고 출처가 담긴 수집 버전을 새로 만든다. 모든 모델 공통 혜택을 한정판만의 가치로 계산하지 않는다.
- '기획 가설'이라고 표시하고 기업의 의도를 확정하지 않는다. 근거와 반증 조건을 함께 적는다.
- KPI는 이름 나열로 끝내지 않는다. 데이터 접근 가능성, 같은 조건의 비교 기준, 각 결과에서 바꿀 결정을 연결한다. 근거 없는 합격 수치를 만들지 않는다.
- 수익 판단은 추가 판매의 기여이익에서 추가 판촉·운영 비용을 뺀다. 판매 대수에서 원화 비용을 빼지 않는다. 원래 발생했을 판매와 구매 시점 이동도 구분한다.
- '내가 담당자라면'은 AI의 접근 예시이며 사용자의 실제 의견·경험·성과가 아니다. My Thought를 대신 채우지 않는다.

## Notion 편집·실습 누적

- 사용자가 저장을 요청했을 때 기존 DB·원문 URL과 전송 기록을 확인해 같은 기사 행을 찾는다. 새 페이지를 중복 생성하지 않는다.
- 수정 전 페이지와 속성을 새 로컬 파일로 백업하고, 요청한 분석 구간과 속성만 수정한다. 개인 메모·실습 결과·기존 상태는 보존한다.
- '내 생각과 실습' 보기: Title / My Thought / 검증 상태 / 실습 결과 / 실습 링크 / Action.
- 검증 상태 선택값은 미시작/진행중/완료/보류, 실습 결과는 텍스트, 실습 링크는 URL. 새 행은 미시작, 결과·링크·My Thought는 빈칸이다. 기존 행의 상태를 초기화하지 않는다.
- 사용자가 실습한 뒤 발견·근거·판단·다음 검증을 기록한다. 조사 설계 완료와 실제 데이터로 가설을 검증한 결과를 구분한다. 파일은 링크로 연결하고 필요하면 상세 본문에 추가한다.
- 수정 후 각 페이지의 속성·본문을 다시 읽고 Source 숨김, 요약 길이, 사용자 작성 값 보존을 확인한다. 부분 실패는 중복 확인 후 실패한 부분만 재시도한다.
- planning.py는 검증과 파일 생성 도구다. Notion 편집은 연결 도구로 수행하며 무인 동기화나 Slack 전송을 구현했다고 주장하지 않는다.
