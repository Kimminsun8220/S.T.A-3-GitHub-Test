# 커리어 인사이트 작성 기준

## 판단 기준

- 사업기획: 기업·사업 전체의 성장, 고객 세그먼트, 유통·서비스 운영, 자원 배분과 수익 구조에서 검토할 의사결정.
- 상품기획: 어떤 고객 문제를 어떤 상품·가격·사양·차별점으로 해결하고 출시 이후 어떻게 개선할지 검토할 의사결정.
- 동일한 요약을 두 관점에 반복하지 않는다. 각 관점에 구체적인 검토 대상과 판단 이유를 담는다.
- 원문이 밝히지 않은 변화 원인·성과·KPI 수치를 만들어 쓰지 않는다. 발표 목표는 달성 실적과 구분한다. 변화 전 자료가 없으면 무엇이 새로 공개됐는지만 말하고, 직무 소개는 변화 확인 불가를 명시한다.
- 확인할 데이터는 실제 수치가 아니라 분석 제안이다. 지표명과 뜻/계산 기준, 필요한 이유, 구할 곳, 접근 가능성을 적는다. 자료가 공개됐는지 확인하지 않았으면 `공개 여부 미확인`, 내부 데이터가 필요하면 `내부 데이터 필요`로 쓴다. 모든 데이터가 공개되어 있다고 가정하지 않는다.
- 취업 활용은 면접·자소서·포트폴리오 중 적합한 항목과 활용 방법을 쓴다. 모든 자료에 세 가지를 강제하지 않는다. 사용자가 기업 사례를 직접 수행한 경험처럼 쓰지 않는다.
- 학습 질문은 자료에서 선택할 수 있는 대안이나 추가 확인할 근거를 묻는다. 모범 답안이나 사용자의 생각을 대신 작성하지 않는다.
- Action은 10~60분 안에 해볼 한 가지 작업과 눈으로 확인할 산출물을 적는다. 원본 데이터가 없어도 수행 가능한 비교표·분석 설계 등으로 제안할 수 있다. 실습 완료나 성과를 미리 주장하지 않는다.
- 발행일 미확인과 오래된 자료는 최신 변화로 포장하지 않는다. 영상 소개문만 읽었다면 영상 답변까지 분석했다고 표현하지 않는다.

## 분석 JSON

최상위는 `analyses` 배열. 수집 items 각각에 URL로 연결되는 분석이 정확히 하나 있어야 한다. held(보류 자료)는 분석하지 않는다.

각 분석은 다음 필드만 갖는다.

- `url`: 수집 원문 주소. 원본 연결용이며 제목·날짜·요약 등은 여기서 수정하지 않는다.
- `what_changed`, `business_view`, `product_view`: 각각 `text`와 `fact_refs`를 갖는 객체. fact_refs는 수집 자료의 사실 요약 1~3번 중 근거가 되는 번호 목록이다. 근거 번호는 해석을 원문 주장으로 바꾸는 표시가 아니다.
- `kpis`: 하나 이상. 각 항목은 `name`, `definition`, `why`, `data_source`, `availability` 문자열. availability는 `공개 자료 확인` / `공개 여부 미확인` / `내부 데이터 필요`. 공개 자료 확인은 실제 읽은 원문에서 해당 데이터가 확인될 때만 사용한다.
- `career_uses`: 하나 이상. 각 항목의 `type`은 `면접` / `자소서` / `포트폴리오`, `how`는 활용 방법.
- `questions`: 하나 이상의 학습 질문 문자열.
- `action`: `task`, `deliverable` 문자열과 `minutes` 정수(10~60).
- `limitations`: 현재 자료만으로 알 수 없는 점을 하나 이상 담은 문자열 목록.

My Thought는 분석 입력에 넣지 않는다. 실행 도구가 수집 원본의 빈칸을 그대로 유지한다. 출력은 기존 수집 JSON 및 그 SHA-256(파일 내용 확인용 지문)을 기록해 어떤 원본에 분석을 붙였는지 확인할 수 있게 한다.
